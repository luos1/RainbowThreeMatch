# Google sign-in and account setup

For the Firebase-backed app, follow [Firebase Spark setup](firebase-setup.md).
The original integration and HTTPS alternative below provide background on
UniversalSDK and the previous in-memory flow.

Rainbow starts in `00.Loading`. Successful Google sign-in opens `01.Lobby`, where Play opens `02.Game`. The lobby returns to sign-in if the app has no session. Sign out clears the Rainbow session and asks the platform SDK to sign out. A cold start requires sign-in again. The game stores the SDK's account identifier in process memory and discards the token after checking that the native SDK returned one. This session gates the local UI. A future server must authenticate requests independently.

## Google OAuth test environment

1. Confirm the first target platform and the final package or bundle identifier. Use a newly provisioned RainbowThreeMatch-only Google Cloud project and Google Auth Platform app. Follow the [AI handoff](AI-HANDOFF.md#dedicated-infrastructure-and-setup-order) for resource separation and provisioning order. Both current Unity identifiers are `com.DefaultCompany.com.unity.template.mobile2D`, a placeholder. Configure the Rainbow app in the project's testing audience with the testers and support contact supplied by the owner. Keep the consent screen in testing for device QA. [Google Auth Platform audience](https://support.google.com/cloud/answer/15549945)
2. For Android, register an Android OAuth client for the final package name and the SHA-1 of the certificate signing the test APK. Register a Web OAuth client in the same Google project. Launch Unity or Gradle from a process that supplies that Web **client ID** in `RAINBOW_GOOGLE_WEB_CLIENT_ID`. The launcher Gradle template emits `google_web_client_id`, the resource read by UniversalSDK 3.0.5. A Play-distributed build with a different signing certificate needs the corresponding Android OAuth registration. [Google Android client authentication](https://developers.google.com/android/guides/client-auth)
3. For iOS, register an iOS OAuth client for the final bundle ID. Supply its **client ID** in `RAINBOW_GOOGLE_IOS_CLIENT_ID` when launching Unity for export. The postprocessor sets the SDK's `GoogleClientID`, the standard `GIDClientID`, and the reversed URL scheme. An existing local UniversalSDK settings asset with Google enabled also works. Verify the generated `Info.plist`, sign with the authorized Apple team and provisioning profile, then test return from the Google account picker on a device. [Google Sign-In for iOS setup](https://developers.google.com/identity/sign-in/ios/start-integrating) · [Unity deep-link callback](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Application-deepLinkActivated.html)
4. Build with the Android or iOS module for Unity `2022.3.8f1` and the matching platform toolchain. On a device, cancel once, retry with an allowed test account, play from the lobby, then confirm sign-out and a second sign-in. The Mac Editor exercises the unsupported-platform path and the same Unity scene flow with a test double.

The client IDs are public app identifiers. Keep OAuth client secrets, signing keys, and service credentials in the selected platform's credential store. No client secret is needed by these Unity build settings. OAuth configuration and mobile signing assets are provided separately from the repository.

Android's current Maven integration uses UniversalSDK `3.0.5` and its legacy Google Sign-In dependency. The unused resolver XML lists `3.0.7`. Device QA must check the resolved Gradle dependency graph. Google's supported direction for Android is Credential Manager. If Android is the distribution target, assess a migration before release and confirm the native bridge and dependencies first. For a planned App Store release, review Apple's login-service requirements and exceptions before choosing the final login options. [Android Credential Manager](https://developer.android.com/identity/sign-in/credential-manager-siwg) · [Apple App Review Guideline 4.8](https://developer.apple.com/app-store/review/guidelines/#login-services)

## Account-scoped high scores

Cross-device scores require authenticated storage. The Unity session does not provide server authorization. The minimal service consists of an HTTPS session endpoint, one score record per account, and authenticated read and update endpoints. Verify the Google ID token signature, issuer, expiry and the allowed audience for the selected app. Identify the account by the verified `sub` claim. Derive ownership from that session on every request and use an atomic maximum update so a retried or slower submission cannot reduce the score. A personal best submitted by the game client can still be forged. A competitive leaderboard needs a separate decision about validating gameplay results. [Google ID token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)

| Candidate | Required setup |
| --- | --- |
| Rainbow-owned Firebase Auth and Firestore | Enable Google sign-in, add the platform apps, authorize the native credential exchange, and enforce owner-only reads and monotonic writes in Security Rules. Adopting the Firebase Unity SDK would require a dependency decision. [Firebase Unity Google sign-in](https://firebase.google.com/docs/auth/unity/google-signin) · [Firebase Security Rules](https://firebase.google.com/docs/rules/rules-and-auth) |
| HTTPS service with a managed database owned by Rainbow | Select a host and store, use Google's supported server-side token verifier, issue a service session, and perform atomic score updates keyed by the verified subject. This can retain the existing Unity native SDK and use Unity's built-in HTTP client. [Google backend authentication](https://developers.google.com/identity/sign-in/ios/backend-auth) |

No Rainbow-owned cloud project, OAuth client IDs, or backend configuration were found in the workspace or the accessible Google Cloud search for Rainbow. Hosting, storage, region, and the app identifiers remain owner decisions. The generated mobile build configuration is ready for authorized public client IDs. Device sign-in and cloud scores require the selected project and platform setup.
